# Execution plan — add cave-16 to the level registry

**Slug:** `add-cave-16`
**Branch:** `feat/add-cave-16`
**Base branch:** `main`
**Engine:** `Engine: om-auto-create-pr (steps: 7, --loop: no)`
**Brief:** Create new game level.

## 🎯 Goal

Add a sixteenth playable cave to BoulderGame's `LEVELS` registry so the campaign continues past
`cave-15`, and prove it correct through the project's own design gate (`npm run level:check`) and
the registry-driven Playwright suite.

## Scope

- `src/lib/levels.ts` — one new `LevelDefinition` (`CAVE_16`) with the invariants doc comment the
  file's convention requires, appended to the `LEVELS` play order.
- Nothing else. `level-invariants`, `level-solver` and `level-progression` iterate the registry, so
  a new cave is covered by the existing suite without touching a test file.

### Non-goals

- No new tile types, mechanics, enemies, keys or timers — the tile alphabet in
  `src/components/game/TileArt.tsx` is closed and new mechanics would be a code change, not a level.
- No level-selector UI, no changes to `GameEntry.tsx` or `TileArt.tsx`.
- No edits to existing caves — the e2e suite asserts their coordinates directly.
- No changes to any e2e spec. If a registry-driven spec fails, the cave is wrong, not the test.
- No pipeline/agentic config bootstrap (see Risks) — that would be unrelated churn on a level PR.

## Design intent (autonomous decision)

The `new-level` skill normally opens by asking the author four intent questions (route shape,
boulder role, bonus puzzle, difficulty). This is an autonomous run with no user in the loop, so the
answers were chosen here and are recorded for review:

- **Route:** a long out-and-back, at or above the weight of the registry's late caves — cave-16 is
  played after `cave-13` (41 moves), `cave-14` (39) and `cave-15` (47), so a short cave would read
  as a step backwards in a progression that is ordered by array index.
- **Boulder role:** obstacle. The cave's single boulder is the bonus gem's only door, and it is the
  one thing in the cave that moves; the quota never touches it.
- **Bonus puzzle:** walled in behind that boulder (the `cave-01`/`cave-09` shape), so the bonus is
  an opt-in risk rather than a detour.
- **Difficulty:** harder than `cave-02` (23 moves) and in the late-cave band.
- **Quota:** three gems rather than two — no cave in the registry has ever asked for more than two,
  and `GameEntry` already renders the quota generically, so this is a difficulty knob that costs no
  code change.

### What was built

`cave-16`, "the nail field":

```
############
#p.......rg#
#.####.#..##
#hhhhh.hhhh#
#..g......e#
#.##########
#.g.......g#
############
```

- **The nail field.** Row 3 is spikes from wall to wall but for the single gap at (3,6) — the only
  crossing in the cave. Both descents the player's instinct reaches for are spiked: (2,1), the
  column-1 shaft every earlier cave has trained them to take, and (2,8) in the top-right nook.
- **The sump.** Row 5 is solid but for (5,1), so row 6 is a ten-tile gallery with one mouth. The
  third quota gem sits at its blind end at (6,10), so it must be walked in and walked back out, and
  the exit at (4,10) is the opposite corner from where that walk ends. This is what makes the route
  44 moves — second longest in the registry, behind `cave-15`'s 47.
- **The nook.** The bonus at (1,10) is walled on every side but (1,9), which holds the boulder. The
  board forces one solution and one order: (2,9) is reachable only through (2,8) and (2,8) only from
  (1,8), so opening the support means the west flank is already clear — the boulder rolls into the
  vacated (1,8) and falls onto the Miner in (2,8), whose only escape is east into (2,9), which is
  also the door to the vacated (1,9).
- **No Skarbek.** `cave-12` through `cave-15` all carry one; this cave's hazard is the field, which
  is fully covered by the winnability proof in a way a Skarbek cave is not (`solveLevel` runs with
  `includeTreasurer: false`). Variety, and a cave whose difficulty the gate can actually vouch for.

## Implementation Plan

### Phase 1: Design and author cave-16

1. Draft the 8×12 grid against the hard constraints in `level-audit.ts` (sealed border, exactly one
   `p` and one `e`, spikes present, every boulder settled at t=0, no boulder in the exit column,
   quota and exit reachable without disturbing a boulder).
2. Append `CAVE_16` to `src/lib/levels.ts` with a doc comment listing the cave's own invariants by
   coordinate, and register it at the end of `LEVELS`.
3. Iterate `npm run level:check` until every audit check for cave-16 passes, and confirm the
   solver's route length puts it in the intended difficulty band.

### Phase 2: Validate the change

1. `npm run level:check` — the full audit over all 16 caves.
2. `npm run lint` and `npm run astro -- check` — ESLint with type-checked rules, plus the Astro
   type-check.
3. `npm run build` — the production SSR build, the last step of the CI chain.
4. `npm run test:e2e` — the Playwright suite; `level-invariants`, `level-solver` and
   `level-progression` pick the new cave up from the registry.

## Risks

- **Cave numbering collision — resolved mid-run.** This run opened as `add-cave-15`: `main` ended at
  `cave-14`, and the competing branch `cez/5d62214d` that also added a `cave-15` had no PR. It was
  merged as PR #20 while this run was setting up, so `main` gained its own `cave-15` and this cave
  was renumbered to `cave-16` before any level code was committed. The plan file, branch and PR were
  renamed to match; the first draft PR (#21, `feat/add-cave-15`) was closed rather than left
  misnamed. Nothing else in the registry moved.
- **Solver budget.** A cave too open for the breadth-first solver reports
  `no route found within N states (budget)` rather than a failure. The fix is more walls, never a
  bigger budget. cave-16 settles at 173 states, so it has ample headroom.
- **Route-length regression.** The first draft of the bottom half was a wide row-4 corridor with
  three descents; it passed every check but solved in 31 moves, below `cave-13`/`cave-14`/`cave-15`.
  The sump replaced it precisely to fix that, which the gate does **not** check — `level:check`
  audits correctness, never interest, so the 44-move figure is the human-facing quality claim and
  the reviewer should weigh it.
- **No agentic pipeline config.** This repository has no `.ai/agentic.config.json` and no tracker
  descriptor, and its GitHub labels are the stock set — there is no `review`, `needs-qa`,
  `priority-*` or `risk-*` label to apply. Label work therefore degrades to logged skips.
  `om-setup-agent-pipeline` was deliberately not run: it would add pipeline configuration and
  repository labels that nobody asked for, as unrelated diff on a level PR. Config values used
  here: base branch `main` (from GitHub's default branch), runs dir `.ai/runs`, validation gate
  taken from the CI chain documented in `CLAUDE.md`.
