# Execution plan — add cave-15 to the level registry

**Slug:** `add-cave-15`
**Branch:** `feat/add-cave-15`
**Base branch:** `main`
**Engine:** `Engine: om-auto-create-pr (steps: 7, --loop: no)`
**Brief:** Create new game level.

## 🎯 Goal

Add a fifteenth playable cave to BoulderGame's `LEVELS` registry so the campaign continues past
`cave-14`, and prove it correct through the project's own design gate (`npm run level:check`) and
the registry-driven Playwright suite.

## Scope

- `src/lib/levels.ts` — one new `LevelDefinition` (`CAVE_15`) with the invariants doc comment the
  file's convention requires, appended to the `LEVELS` play order.
- Nothing else. `level-invariants`, `level-solver` and `level-progression` iterate the registry, so
  a new cave is covered by the existing suite without touching a test file.

### Non-goals

- No new tile types, mechanics, enemies, keys or timers — the tile alphabet in
  `src/components/game/TileArt.tsx` is closed and new mechanics would be a code change, not a level.
- No level-selector UI, no changes to `GameEntry.tsx` or `TileArt.tsx`.
- No edits to existing caves — the e2e suite asserts their coordinates directly.
- No changes to any e2e spec. If a registry-driven spec fails, the cave is wrong, not the test.
- No pipeline/agentic config bootstrap (see Risks) — that would be unrelated churn on a level PR.

## Design intent (autonomous decision)

The `new-level` skill normally opens by asking the author four intent questions (route shape,
boulder role, bonus puzzle, difficulty). This is an autonomous run with no user in the loop, so the
answers were chosen here and are recorded for review:

- **Route:** a long out-and-back lap, at or above `cave-13`'s weight — the registry's late caves are
  the hard ones and cave-15 sits after them.
- **Boulder role:** obstacle plus chain — boulders plug the short way home and one stack has to be
  undermined deliberately.
- **Bonus puzzle:** walled in behind a boulder (the `cave-01`/`cave-09` shape), so the bonus is an
  opt-in risk rather than a detour.
- **Difficulty:** harder than `cave-02`, in line with `cave-13`/`cave-14`.
- **Quota:** three gems rather than two — no cave in the registry has ever asked for more than two,
  and `GameEntry` already renders the quota generically, so this is a difficulty knob that costs no
  code change.

## Implementation Plan

### Phase 1: Design and author cave-15

1. Draft the 8×12 grid against the hard constraints in `level-audit.ts` (sealed border, exactly one
   `p` and one `e`, spikes present, every boulder settled at t=0, no boulder in the exit column,
   quota and exit reachable without disturbing a boulder).
2. Append `CAVE_15` to `src/lib/levels.ts` with a doc comment listing the cave's own invariants by
   coordinate, and register it at the end of `LEVELS`.
3. Iterate `npm run level:check` until every audit check for cave-15 passes, and confirm the
   solver's route length puts it in the intended difficulty band.

### Phase 2: Validate the change

1. `npm run level:check` — the full audit over all 15 caves.
2. `npm run lint` and `npm run astro -- check` — ESLint with type-checked rules, plus the Astro
   type-check.
3. `npm run build` — the production SSR build, the last step of the CI chain.
4. `npm run test:e2e` — the Playwright suite; `level-invariants`, `level-solver` and
   `level-progression` pick the new cave up from the registry.

## Risks

- **Cave numbering collision.** Branch `cez/5d62214d` (pushed to `origin`, commit `19eacf2`, **no
  PR opened**) also adds a `cave-15` and is not merged into `main`. `main` currently ends at
  `cave-14`, so `cave-15` is the correct next id for this PR; whichever of the two lands second has
  to renumber. Flagged in the PR body so a reviewer sees it before merging.
- **Solver budget.** A cave too open for the breadth-first solver reports
  `no route found within N states (budget)` rather than a failure. The fix is more walls, never a
  bigger budget.
- **Skarbek caveat.** `solveLevel` runs with `includeTreasurer: false`, so a cave with a `t` in it
  is not covered by the winnability proof the way the others are. Taken into account when placing
  any Skarbek niche: it must be sealed at t=0 and off every route.
- **No agentic pipeline config.** This repository has no `.ai/agentic.config.json` and no tracker
  descriptor, and its GitHub labels are the stock set — there is no `review`, `needs-qa`,
  `priority-*` or `risk-*` label to apply. Label work therefore degrades to logged skips.
  `om-setup-agent-pipeline` was deliberately not run: it would add pipeline configuration and
  repository labels that nobody asked for, as unrelated diff on a level PR. Config values used
  here: base branch `main` (from GitHub's default branch), runs dir `.ai/runs`, validation gate
  taken from the CI chain documented in `CLAUDE.md`.
